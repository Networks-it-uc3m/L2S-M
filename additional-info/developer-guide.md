# Developer guide

This guide explains how this repository is organized and how to build, develop,
test, deploy, and extend L2S-M. It is intended for developers working directly
with this repository, not only for users applying the published deployment
manifests.

For a general explanation of the L2S-M architecture and how the component works
at runtime, start with the [additional information README](./README.md), the
[general usage guide](./general-use.md), the [implementation notes](./implementation.md),
and the [inter-cluster guide](./inter-cluster.md).

## 1. Code overview

L2S-M is implemented in Go as a Kubernetes operator. The controller manager
watches Kubernetes resources, reconciles the desired state, and coordinates the
networking components required to provide L2 virtual networks for pods.

The project is built with [Kubebuilder](https://book.kubebuilder.io/). Kubebuilder
provides the operator framework, the controller-runtime integration, the project
layout, and the code generation flow used for CustomResourceDefinitions (CRDs),
RBAC, webhooks, and controller scaffolding. When extending the operator, use the
Kubebuilder guide as the main reference for the controller and reconciliation
model.

The most important Go dependencies are:

- `sigs.k8s.io/controller-runtime`: controller manager, clients, reconcilers,
  webhooks, health checks, and metrics integration.
- `k8s.io/api`, `k8s.io/apimachinery`, and `k8s.io/client-go`: Kubernetes API
  types, runtime machinery, and Kubernetes client support.
- `github.com/k8snetworkplumbingwg/network-attachment-definition-client`: Multus
  `NetworkAttachmentDefinition` API types.
- `github.com/Networks-it-uc3m/LPM`: integration with the LPM monitoring
  component.
- `github.com/Networks-it-uc3m/l2sm-switch`: switch and overlay support used by
  L2S-M.
- `github.com/Networks-it-uc3m/l2sm-dns`: DNS-related support for L2S-M.
- `google.golang.org/grpc`: gRPC communication with external components.
- `github.com/onsi/ginkgo/v2` and `github.com/onsi/gomega`: test framework and
  assertions.

Kustomize is used to compose the Kubernetes installers under `config/`. Some
resources are generated by Kubebuilder and controller-tools, while other patches
and overlays are maintained by this repository. The generated installer files
under `deployments/` are built from these Kustomize configurations.

The `Makefile` is the main entry point for development tasks. It wraps code
generation, formatting, testing, local Kind cluster setup, development
deployment, CRD installation, Docker image builds, and installer generation.

## 2. Repository structure

### `api/v1/`

This directory contains the Go API types for L2S-M custom resources. It is
Kubebuilder-based code that has been edited for this project.

CRDs are generated automatically from these Go types and their Kubebuilder
markers. After changing API types, run:

```sh
make generate
make manifests
```

To add a new namespaced CRD and controller, scaffold it with Kubebuilder:

```sh
kubebuilder create api --group l2sm --version v1 --kind <KindName> --resource --controller
```

Then edit the generated files in `api/v1/` and the controller under
`internal/controller/`. Kubebuilder generates the starting point; the repository
logic is added afterwards.

### `additional-info/`

This directory contains repository documentation and background material:

- `README.md`: general explanation of how L2S-M works.
- `general-use.md`: how to use L2S-M once installed.
- `implementation.md`: implementation details.
- `inter-cluster.md`: inter-cluster networking information.
- `developer-guide.md`: this guide.
- Presentation material, such as `OSM#13 Plenary Meeting.pdf`.

### `assets/`

Contains images used by the repository documentation.

### `bin/`

Generated locally. The Makefile installs helper binaries here, including:

- `kustomize`: used to build Kubernetes manifests from `config/`.
- `controller-gen`: used to generate CRDs, RBAC, webhooks, and deepcopy code.
- `setup-envtest`: used by controller-runtime tests.
- `golangci-lint`: used by `make lint`.
- `addlicense`: used by `make add-license` to add the repository license header
  to source and documentation files.

Do not commit local tool binaries unless the project explicitly changes its
policy.

### `cmd/`

Contains the controller manager entry point in `cmd/main.go`. This is mostly
Kubebuilder-managed wiring: scheme registration, manager creation, controller
registration, webhook registration, health checks, and startup.

In normal development, do not edit this file unless a new controller, webhook,
scheme, manager option, or runtime dependency actually requires it. Kubebuilder
also modifies this file when scaffolding new APIs/controllers.

### `config/`

Contains the Kustomize resources used to install and deploy L2S-M.

Some folders are generated or heavily influenced by Kubebuilder/controller-tools:

- `config/crd/`: generated CRD bases and CRD kustomization.
- `config/rbac/`: generated and maintained RBAC resources.
- `config/webhook/`: webhook manifests.
- `config/samples/`: sample custom resources.

Other folders are maintained by this repository:

- `config/manager/`: controller manager deployment configuration. This is where
  the controller manager workload is defined.
- `config/default/`: default installation overlay.
- `config/dev/`: development overlay used when running the controller locally
  while installing the webhooks and related cluster resources.
- `config/codeco/`: installation overlay for the CODECO project.
- `config/sdncontroller/`, `config/certmanager/`, and `config/prometheus/`:
  supporting resources and integrations.

The three main top-level installation configurations are:

- `config/default/`: standard L2S-M installation.
- `config/dev/`: developer deployment for local controller execution.
- `config/codeco/`: CODECO-specific installation.

### `deployments/`

Contains generated full-installation YAML files built from `config/` with
Kustomize.

Current generated installers include:

- `deployments/l2sm-deployment.yaml`: default L2S-M deployment.
- `deployments/codeco-deployment.yaml`: CODECO deployment.

These files are generated by Makefile targets and should not be edited manually.
Change `config/` and rebuild the installers instead.

### `examples/`

Contains runnable examples of L2S-M use cases. Each example includes its own
README explaining how to deploy and use it. Examples include quickstart,
ping-pong, overlay setup, inter-cluster setup, CODECO, quarantine, CDN, and
other scenarios.

### `internal/`

Contains most of the implementation code.

#### `internal/controller/`

Contains the reconcilers and webhook logic. This code is initially scaffolded by
Kubebuilder and then edited by this repository.

There is one controller per custom resource, plus pod-related controller and
webhook logic:

- `L2Network`
- `NetworkEdgeDevice`
- `Overlay`
- `QuarantinePodRequest`
- `Pod`
- Pod mutation webhook logic

When editing controllers, follow the Kubebuilder reconciliation model: read the
observed cluster state, compare it with the desired state, apply the minimum
changes needed, update status where appropriate, and return a clear reconcile
result or error.

#### Interface packages

These packages isolate integration with external components and Kubernetes
networking conventions:

- `internal/lpminterface/`: integration with LPM for monitoring.
- `internal/networkannotation/`: Multus and network annotation handling.
- `internal/sdnclient/`: client code for the SDN controller.
- `internal/talpainterface/`: integration with the switches used in the overlay.

Other internal packages include:

- `internal/utils/`: general-purpose helper methods used across the repository.
- `internal/env/`: environment variable handling.
- `internal/monitoringnetwork/`, `internal/dnsinterface/`, and `internal/ids/`:
  supporting implementation packages for specific L2S-M features.

### `test/e2e/`

End-to-end tests for the L2S-M application. These tests are intended to run
against a Kubernetes environment, normally a Kind cluster prepared by the
development workflow.

### `test2/`

Benchmark and experiment-oriented tests. For example, this directory includes
self-healing timing tests.

### Root files

- `Dockerfile`: builds the controller manager image.
- `Makefile`: manages the repository workflow.
- `PROJECT`: Kubebuilder project metadata. Do not edit manually unless you know
  how Kubebuilder uses this file.
- `VERSION`: source of truth for the default image tag used by the Makefile.
- `go.mod` and `go.sum`: Go module definition and dependency lock files.
- `.env`: local development environment values used by the Makefile and
  `make run`.

## 3. Makefile workflow

Use `make help` to print the available targets grouped by category.

### Code generation and local checks

```sh
make manifests
```

Generates webhook configuration, RBAC, and CRD objects using `controller-gen`.
CRD output is written under `config/crd/bases`.

```sh
make generate
```

Generates Go deepcopy methods such as `DeepCopy`, `DeepCopyInto`, and
`DeepCopyObject`.

```sh
make fmt
make vet
```

Runs `go fmt ./...` and `go vet ./...`.

```sh
make test
```

Runs generation, formatting, vetting, installs envtest assets, and runs Go tests
except the e2e package. It writes coverage to `cover.out`.

```sh
make test-e2e
```

Runs the Ginkgo end-to-end test suite in `test/e2e/` against a Kubernetes
cluster.

```sh
make lint
make lint-fix
```

Runs `golangci-lint`, optionally with automatic fixes.

### Build

```sh
make build
```

Generates manifests and code, formats, vets, and builds the manager binary at
`bin/manager`.

```sh
make docker-build
make docker-push
```

Builds and pushes the controller manager image for the current platform.

The image name defaults to:

```txt
alexdecb/l2sm-controller-manager:<contents of VERSION>
```

You can override it without editing the Makefile:

```sh
make docker-build IMG=<registry>/<image>:<tag>
make docker-push IMG=<registry>/<image>:<tag>
```

For the project release workflow, update the image registry/account if needed
and use:

```sh
make docker-buildx
```

This target creates a Docker Buildx builder, builds a multi-architecture image,
pushes it, and removes the builder. By default it targets:

```txt
linux/arm64,linux/amd64,linux/s390x,linux/ppc64le
```

### Installer generation

```sh
make build-installer
```

Regenerates `deployments/l2sm-deployment.yaml` from `config/default/`.

```sh
make build-codeco
```

Regenerates `deployments/codeco-deployment.yaml` from `config/codeco/`.

Both targets update the controller image in `config/manager/` before building
the final YAML.

### Cluster installation and deployment

```sh
make install
```

Installs the CRDs into the Kubernetes cluster selected by `~/.kube/config`.

```sh
make uninstall
```

Removes the CRDs. Use `ignore-not-found=true` to ignore missing resources:

```sh
make uninstall ignore-not-found=true
```

```sh
make deploy
make undeploy
```

Deploys or removes the default controller manager installation using
`config/default/`.

```sh
make deploy-dev
make undeploy-dev
```

Deploys or removes the development overlay from `config/dev/`. The development
deployment installs CRDs and webhook configuration while the controller itself is
run locally with `make run`.

```sh
make run
```

Runs the controller manager locally from `cmd/main.go`. This target also runs
manifest generation, code generation, formatting, and vetting first.

### Development cluster helpers

```sh
make create-cluster
```

Creates a Kind cluster using `examples/quickstart/kind-cluster.yaml`.

```sh
make install-requisites
```

Installs the networking prerequisites for local development. This target calls
`make add-cni`, waits for pods, installs cert-manager, installs Multus, and
waits again.

```sh
make add-cni
```

Downloads CNI plugins into `plugins/bin` if needed, copies them into Kind nodes,
enables required node settings, and installs Flannel.

```sh
make clean
make delete-cluster
```

Deletes Kind clusters. `delete-cluster` targets the `l2sm-test` cluster and also
removes the local `plugins/` directory.

```sh
make copy-to-container container=<container_name>
```

Copies local CNI plugins into a specific container.

### Webhook certificates

```sh
make webhook-certs
```

Generates local self-signed webhook certificates under
`/tmp/k8s-webhook-server/serving-certs`, using `DEV_IP` from `.env`.

`make deploy-dev` uses these certificates and patches
`config/dev/webhookcainjection_patch.yaml` with the generated CA bundle and the
local webhook URL.

### Tools and license headers

```sh
make install-tools
make add-license
```

Installs `addlicense` into `bin/` and applies the repository license header to
Go, JSON, YAML, YML, and Markdown files.

## 4. General development workflow

### Adding or changing a CRD

For a new CRD, scaffold the API and controller with Kubebuilder:

```sh
kubebuilder create api --group l2sm --version v1 --kind <KindName> --resource --controller
```

Then:

1. Edit the API type in `api/v1/`.
2. Edit the reconciler in `internal/controller/`.
3. Add or update tests for the API/controller behavior.
4. Regenerate code and manifests:

```sh
make generate
make manifests
```

The CRDs are generated automatically from the API types and Kubebuilder markers.
Do not manually edit generated CRD YAML when the change belongs in the Go API.

### Local debug workflow

A typical local development loop is:

```sh
make create-cluster
make install-requisites
make generate
make install
make deploy-dev
```

Then edit `.env` with the controller address used by the local run. The
controller port is normally:

```txt
CONTROLLER_PORT=30000
```

The controller IP must be the Kind control-plane container IP address. It is
usually similar to `172.18.0.2`, but check the actual Docker container instead
of assuming it.

After `.env` is correct, run the controller locally:

```sh
make run
```

Then debug, enhance, regenerate, reinstall CRDs when needed, and repeat.

When changing only controller logic, `make run` is usually enough because it
already runs generation, formatting, and vetting. When changing CRD schemas,
remember to run `make generate` and `make install` so the cluster has the
updated CRDs.

### Release workflow

When the code is ready:

1. Update `VERSION`.
2. Build and push the multi-architecture controller manager image:

```sh
make docker-buildx
```

3. Regenerate the default installer:

```sh
make build-installer
```

4. If publishing the CODECO installer too, regenerate it:

```sh
make build-codeco
```

5. Review the generated files under `deployments/` before committing.

## 5. What to edit and what not to edit

Edit these files and directories during normal development:

- `api/v1/` for API types and Kubebuilder markers.
- `internal/controller/` for reconciliation and webhook behavior.
- Interface packages under `internal/` for integration logic.
- `config/default/`, `config/dev/`, `config/codeco/`, `config/manager/`, and
  other maintained Kustomize overlays when deployment behavior changes.
- `examples/` when adding or updating user-facing scenarios.
- Tests under `internal/`, `test/`, and `test2/`.
- `VERSION` when preparing a release.

Avoid manual edits to generated outputs:

- `api/v1/zz_generated.deepcopy.go`
- Generated CRD bases under `config/crd/bases/`
- Generated RBAC when the source of truth is Kubebuilder markers
- Generated installers under `deployments/`
- Local binaries under `bin/`

Generated files should be changed by updating the source Go code, markers,
Kustomize overlays, or Makefile inputs, then rerunning the relevant `make`
target.
